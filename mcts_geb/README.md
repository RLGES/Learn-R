# mcts_geb

Monte Carlo Tree Search over Learn-R's e-graph rewrite rules — adapted
from the `Untitled84 (5).ipynb` MCTS-GEB prototype, but wired into
**this repo's actual rule sources** instead of a standalone toy rule set:

- **Static rules**: the algebraic / strength-reduction identities defined
  in `egraph_bridge/egg_egraph.py` (`create_algebraic_rules()`,
  `create_strength_reduction_rules()`, etc.) — the egglog equivalents of
  the hand-written `rewrite_rules/tier*` rules.
- **Learned rules**: rules generated by the repo's real LLM pipeline
  (`learned_rules/llm_rule_generator.py` → `rule_parser.py` →
  `rule_filter.py` → `rule_to_egglog.py`). No API key needed to try it —
  with no `.env` configured it automatically falls back to a
  deterministic stub LLM response, so the whole pipeline (including
  parsing/filtering/converting) still runs and produces real rules.

## Where this lives

```
Learn-R-main/
└── mcts_geb/              <- new package, sits next to egraph_bridge/, learned_rules/, etc.
    ├── __init__.py
    ├── rulesets.py         # builds the MCTS action space (static + learned rulesets)
    ├── search.py           # MCTS engine (Node, UCB1, mcts_construct, plain_saturation)
    ├── test_cases.py       # sample expressions to optimize
    ├── run_experiment.py   # CLI entry point
    └── README.md           # this file
```

It's a plain subpackage of the repo (imports `egraph_bridge`,
`learned_rules`, etc. the same way `pipeline/` does), so it should be
dropped straight into the repo root as `mcts_geb/`.

## Requirements

```bash
pip install egglog
```

Everything else (the LLM pipeline, Z3 verification, etc.) is already
in `requirements.txt`; those pieces degrade gracefully if their
optional deps (`openai`, `anthropic`, `z3-solver`, ...) aren't
installed — you'll just get the stub LLM output / skipped verification
instead of an error.

## Running it

```bash
cd Learn-R-main
python -m mcts_geb.run_experiment
```

Useful flags:

```bash
# static rules only, skip LLM generation entirely
python -m mcts_geb.run_experiment --no-llm

# use a real LLM provider (needs a configured .env, see .env.example)
python -m mcts_geb.run_experiment --provider anthropic

# also verify learned rules with Z3 before using them (needs z3-solver)
python -m mcts_geb.run_experiment --verify

# tune the search
python -m mcts_geb.run_experiment --simulations 200 --steps 10 --rollout-depth 6
```

This prints a comparison table (MCTS-found cost vs. plain
equality-saturation baseline cost, per test case) and writes
`mcts_geb/results.json` and `mcts_geb/results.csv`.

## How it works

1. `rulesets.build_action_space()` builds a flat list of `(name, egglog.Ruleset)`
   pairs — **one rule per Ruleset** (not bundled), so each is an
   independently selectable MCTS action, exactly like the notebook's
   `RULES = [r_mul_one, r_mul_zero, ...]`.

2. `search.mcts_construct()` runs classic MCTS (UCB1 selection, random
   expansion, random rollout, backprop) where:
   - a **node** = a committed sequence of actions (rule applications)
   - **applying an action** = `eg.run(1, ruleset=RULES[a])` on a
     freshly rebuilt e-graph replaying the whole committed sequence
     (mirrors the notebook's `replay()`)
   - **reward** = `max(initial_cost - rollout_cost, 0)`
   - after each batch of simulations at the root, the single
     best-scoring child action is committed, and search continues from
     there for `--steps` rounds.

3. `search.plain_saturation()` is the baseline: combine every rule into
   one `unstable_combine_rulesets(...)` and run standard egglog
   saturation for `--sat-iters` iterations — i.e., "just apply
   everything until it settles," with no search at all.

4. `test_cases.py` has 9 sample expressions — pure algebraic ones (dead
   code, strength reduction, cancellation) and ones built from actual
   assembly instruction sequences via the same `ExprBuilder` /
   `RuleToEgglogConverter._parse_instructions_to_expr` the rest of the
   repo uses, so the test cases stay grounded in real instruction
   sequences rather than pure math.

## A finding worth knowing about

Running this surfaced a real limitation in `learned_rules/rule_to_egglog.py`:
`RuleToEgglogConverter` currently converts a rule's LHS/RHS registers
into **concrete** `Asm.var("r1")` expressions rather than **pattern**
variables. That means a learned rule generated from a window using
register name `r1` will only match expressions that literally use the
variable name `"r1"` — it won't generalize to `"x"`, `"eax"`, or any
other register. You can see this directly:

```python
# learned rule: ADD r1,1 / ADD r1,1  ->  ADD r1,2
# matches:
(Asm.var("r1") + Asm(1)) + Asm(1)   # -> Asm.var("r1") + Asm(2)   ✓ fires
# does NOT match:
(Asm.var("x")  + Asm(1)) + Asm(1)   # -> unchanged                ✗ doesn't fire
```

This is why, in the sample results, learned rules only help test cases
that happen to reuse the same variable name the rule was generated
from. If you want learned rules to generalize the way the static rules
do (which use egglog `var("x", Asm)` pattern variables, not concrete
ones), that converter would need to bind LHS operand names to egglog
pattern variables instead of literal `Asm.var(name)` calls.
